# Golden evaluation set

73 queries over the private job-advertisement corpus, with relevance judgements
derived by rule rather than written by hand.

| File | Committed | Contents |
|---|---|---|
| `queries.jsonl` | yes | The queries, their class, and the **rule** that resolves each one to a document set |
| `relevance_hashed.jsonl` | yes | Per-query relevant-document **counts and hashes** (`sha256(job_id)[:20]`) |
| `summary.json` | yes | Set-level statistics |
| `routing_probes.jsonl` | yes | 22 held-out routing questions used to *tune* the router |
| `routing_heldout.jsonl` | yes | 18 routing questions written after tuning and never tuned on |
| `data/private/retrieval/golden/resolved.jsonl` | **no** | The same judgements with real advertisement ids |

The hash is a de-identifier, not a secret. It is unsalted, and advertisement
ids are short numeric strings, so anyone holding the id space can recompute the
mapping. That is deliberate. Salting would make the committed file
irreproducible for a reader running the pipeline on their own corpus, and the
most the mapping recovers is which public listing matched a public query. The
control that matters is the one above it in the table: advertisement *text*
and the ids that resolve to it stay in `data/private/`.

## Why rules instead of hand-written judgements

Writing 61 × ~25 relevance judgements by hand would take most of a day, would
not be reproducible by anyone else, and would drift as the corpus is refreshed.
Instead each query carries a predicate that resolves against the corpus, so
the *derivation* is what gets committed and the resolution is regenerated by
`scripts/build_golden_set.py`. Three of the four rule types reuse work this
project had already done and validated.

| Rule | Ground truth | Queries |
|---|---|---|
| `alias_match` | Word-boundary match of a term in title + description | 22 |
| `skill_match` | The dictionary skill extractor's `skill_mentions` table | 21 |
| `label_match` | The 244-advertisement hand-adjudicated label set | 12 |
| `metadata_match` | Cleaned corpus metadata (city, source, role, seniority) | 6 |
| `all_of` | Intersection of the above; used for every mixed query | 12 |

## Query classes

Metrics are always reported per class. An overall mean across these three would
describe none of them.

- **lexical** (22) — a named tool or technology: `dbt`, `Terraform`, `Power BI`.
  Answered by exact term matching.
- **semantic** (22) — a paraphrase with deliberately little vocabulary overlap
  with the advertisements: *"roles where you would explain results to people
  without a technical background"*.
- **mixed** (12) — a lexical clause and a semantic clause in one sentence:
  *"Python roles in Melbourne that involve explaining results to non-technical
  people"*. Added after the first results, because a set whose queries are each
  cleanly one type cannot test a router that must pick one type. Relevance is
  the intersection of the clauses.
- **aggregation** (17) — counting, share, ranking or comparison questions.
  These are in the set **to demonstrate that retrieval cannot answer them**,
  not because retrieval is expected to do well.

## Known biases and limits

**The label-derived queries can only test what the labelling scheme covers.**
The 244-advertisement scheme has four dimensions (role, entry fit, AI signal,
coding signal). Queries derived from it inherit that shape, so the semantic
class over-represents those concepts and under-represents everything else a
person might ask a job corpus.

**Judgement incompleteness differs by rule type, and is corrected for.**
`alias_match`, `skill_match` and `metadata_match` resolve over all 705
advertisements, so their judgements are complete. `label_match` can only judge
the 244 labelled ones. Scoring those against the full corpus would count an
unjudged advertisement as a miss and would make semantic queries look worse
than lexical ones for a reason unrelated to retrieval. Label-derived queries
therefore carry `judged_pool: "labelled"` and are scored on a **condensed
ranking**: unjudged advertisements are removed from the ranking rather than
counted against it. The trade is that those queries are measured on a smaller
corpus.

**`skill_match` queries risk circularity, and this is measured.** The skill
dictionary matches aliases with a regular expression, and BM25 matches terms —
so a golden set built from dictionary hits could favour BM25 by construction.
Twelve of the 22 lexical queries therefore use tools that are **not** in the
dictionary (`Terraform`, `Fivetran`, `BigQuery`, `Redshift`, `Grafana`,
`Datadog`, `Scala`, `TypeScript`, `Postgres`, `Jira`, `Splunk`, `Salesforce`),
judged by direct string match. `reports/retrieval/ablation_lexical_dictionary_bias.csv`
reports the two subsets separately. They behave the same — dense retrieval
scores nDCG@10 0.508 inside the dictionary and 0.565 outside it — so the
lexical result is not an artefact of the dictionary.

**Relevant-set sizes vary a lot, which caps recall@k.** Lexical queries have a
median of 10.5 relevant advertisements; aggregation queries have 51 and reach
705. recall@10 is bounded above by `min(10, |relevant|) / |relevant|`, so an
aggregation query's recall@10 cannot exceed 0.18 on average no matter how good
the ranker is. **nDCG@10 is the primary metric** for that reason: its ideal
gain is capped at `min(k, |relevant|)`, which normalises for set size.
`recall_at_10_ceiling` is published beside every recall figure.

Two queries originally written as semantic (`entry_fit = Experienced role`,
matching 124/244; `coding_signal = No coding signal`, matching 162/244) were
reclassified as aggregation. Asking a ranker to surface most of the corpus is a
population question wearing a search question's clothes.

**73 queries is a small evaluation set.** The bootstrap half-width on the
baseline configuration's recall@10 is **0.076**. Differences smaller than about
8 points are inside the resampling noise of a set this size and should not be
read as real. Per-class intervals are published with every figure, and the
paired tests in `reports/retrieval/paired_comparisons.csv` are more sensitive
than comparing two separate intervals.

**The mixed class is the smallest and the most important to grow.** Twelve
queries establish that routing has a failure mode on blended constraints, not
how large it is. It is also the only class whose relevance comes from an
intersection of rules, which yields small relevant sets (median 7).

## Regenerating

```bash
python scripts/build_golden_set.py
```

Reads `queries.jsonl`, resolves each rule against the private corpus, writes
real ids to `data/private/` and hashes to `relevance_hashed.jsonl`.
`tests/test_retrieval_privacy.py` fails if an advertisement id or a fragment of
advertisement text ever appears in a committed file.
